# HS Security & Services — وضعیت توسعه

این تغییرات روی شاخهٔ `feat/hs-security-services` توسعه داده شده‌اند. تست‌های واحد و DOM جای تست نصب روی سرور واقعی را نمی‌گیرند. **Fair Use در این نسخه فقط سیاستِ پیش‌نویس و پیش‌نمایش دارد؛ محدودیت سرعت اعمال نمی‌کند.**

| بخش | پیاده‌سازی | محدودیت فعلی |
| --- | --- | --- |
| ناوبری HS | کنترل واحد فلش، زیرمنو و تب‌های بالای صفحه | با DOM نمایندهٔ پنل تست شده؛ نسخهٔ نصب‌شده باید بررسی شود |
| Firewall | Observe/Enforce، allow/block شبکهٔ IPv4/IPv6، محافظت SYN، تأیید و برگشت ۴۵ ثانیه‌ای | فقط INPUT میزبان؛ ترافیک FORWARD داکر و حمله‌ای که لینک بالادست را اشباع کند خارج از این لایه است |
| Certificates | فهرست گواهی TLS پنل، گواهی اعتماد نود و گواهی‌های عامل، تاریخ انقضا و عملیات تمدید | تمدید خودکار فقط گواهی قابل مدیریت با Certbot؛ چرخش گواهی اعتماد نود هنوز خودکار نیست |
| WARP | وارد کردن پروفایل WireGuard، انتخاب Core، مسیریابی دامنه/inbound، پیش‌نمایش و اعمال با کنترل نسخهٔ Core | Xray؛ ثبت حساب WARP و تست اتصال خارجی خودکار نشده است |
| Telegram proxy | ساخت، start/stop/delete، نمایش وضعیت سرویس و لینک `tg://proxy` با padding | به binary رسمی MTProxy و عامل روی سرور انتخابی نیاز دارد؛ FakeTLS و سهمیهٔ هر کاربر در این مرحله نیست |
| Fair Use | آستانهٔ مستقل Host، درصد سرعت، مبنای Mbps، محاسبهٔ مصرف هر کاربر، علامت Fair limited در سیاست | **Draft only**؛ فعال‌سازی Feature عمداً 409 برمی‌گرداند؛ نه سرعت و نه سابسکریپشن کاربر تغییر نمی‌کند |

## ناوبری و دلیل باگ قبلی

`hs-tab-fix.js` قبلاً تمام کلیک‌های داخل `hs-plugin-nav` را در capture phase متوقف می‌کرد؛ فلش و زیرمنو به handler اصلی نمی‌رسیدند. همچنین صفحهٔ دوم و قدیمیِ Features را بدون تب Firewall می‌ساخت. اکنون مالک ناوبری `hs-plugin.js` است و فایل سازگاری فقط بخش Features و یافتن outlet را فراهم می‌کند.

API فایروال در `app/hs_shield_api.py` نصب می‌شد، اما `app.routers` آن را از `.` وارد می‌کرد. مسیر به `from app import hs_shield_api` اصلاح شده است؛ خطای import نیز در log ثبت می‌شود.

## نصب و به‌روزرسانی آزمایشی

تا پیش از merge، دستور معمول `hs-pg update` این شاخه را نصب نمی‌کند. برای آزمایش روی محیط staging، اسکریپت همین شاخه را دریافت و با `--ref feat/hs-security-services` اجرا کنید. تغییرات Core و فعال‌سازی Enforce را از UI انجام دهید. نصب با `--restart` مانند قبل فرایند پنل را ری‌استارت می‌کند.

فایل‌ها در `/opt/hs-pg` و state پنل در `/var/lib/pasarguard/hs-plugin` قرار می‌گیرند. integrator فایل‌های API/JS را پس از جایگزینی container بازاعمال می‌کند. تغییر ساختار upstream که anchorها را نامعتبر کند، باید ابتدا بررسی شود؛ ادعای سازگاری با هر نسخهٔ آینده وجود ندارد.

## Firewall

- حالت اولیه `observe` است.
- Linux، nftables و systemd برای enforce لازم‌اند.
- ابتدا پورت‌های مدیریت را تنظیم کنید؛ حداقل یک پورت اجباری است. loopback و اتصال‌های established/related حفظ می‌شوند.
- قواعد allow قبل از block ارزیابی می‌شوند.
- SYN rate به‌ازای هر source IP محاسبه می‌شود؛ `auto_stage` فقط هنگام Elevated/Attack این محافظت را فعال می‌کند.
- nftables کل قواعد خودش را در یک transaction به‌روزرسانی می‌کند؛ هیچ `flush ruleset` اجرا نمی‌شود. جدول اختصاصی `inet hs_plugin` است.
- پیش از اعمال، `nft --check` اجرا می‌شود. یک timer مستقل قبل از تغییر قواعد مسلح می‌شود. برای نگه‌داشتن سیاست جدید، دکمهٔ **Keep this policy** را در مهلت نمایش‌داده‌شده بزنید. بدون تأیید، فقط جدول HS حذف می‌شود.
- سیاست تأییدشده روی disk نگه‌داری و پس از restart عامل بازاعمال می‌شود. سیاستی که به علت عدم تأیید برگشته، بدون تغییر یا خاموش/روشن کردن مجدد تلاش نمی‌شود.
- توقف/خرابی عامل با `ExecStopPost` جدول HS را حذف می‌کند. سیاست آخر هنگام راه‌اندازی مجدد دوباره بررسی می‌شود.
- آمار packet و throughput شامل RX+TX رابط‌هاست. رابط‌های مجازی ممکن است ترافیک forwarded را دوباره در مجموع بشمارند؛ این مقدار اندازه‌گیری ظرفیت لینک یا اثبات حمله نیست.

## عامل گواهی و سرویس نود

روی میزبان پنل، `hs-services-agent.service` هنگام نصب افزونه نصب می‌شود. برای نود:

1. در Certificates → Node agents، برای نود مربوطه token بسازید. صدور مجدد token قبلی را باطل می‌کند.
2. روی همان نود، token را داخل `/etc/hs-pg/agent-token` با دسترسی `600` ذخیره کنید؛ آن را در history فرمان قرار ندهید.
3. اسکریپت `plugin/install-node-agent.sh` از **همین revision/شاخه** را روی نود اجرا کنید:

```bash
sudo env HS_REF=feat/hs-security-services bash install-node-agent.sh \
  https://panel.example.com 3 /etc/hs-pg/agent-token
```

عدد `3` شناسهٔ نود در پنل است. عامل تنها از طریق HTTPS و token محدود به همان نود، گزارش می‌فرستد و job می‌گیرد؛ هیچ فرمان shell دلخواه از API پذیرفته نمی‌شود. نتیجهٔ عملیات قبل از ارسال در فایل محلی ثبت و بعد از قطع موقت ارتباط دوباره ارسال می‌شود. اجرا مجدداً تکرار نمی‌شود. lease گم‌شده به وضعیت `interrupted` می‌رود و نتیجهٔ دیررس با همان lease قابل ثبت است.

### گواهی‌ها و فعال شدن تمدید

عامل گواهی‌های `/etc/letsencrypt/live/*/fullchain.pem` را پیدا می‌کند. در `/etc/hs-pg/services.json` می‌توان گواهی‌های دستی را برای پایش اضافه کرد و واحد قابل reload را برای Certbot تعریف کرد:

```json
{
  "certificates": [
    {"id": "node-server", "path": "/var/lib/pasarguard-node/ssl_cert.pem", "provider": "manual"}
  ],
  "reload_units": {"panel.example.com": "nginx.service"}
}
```

مسیر گواهی دستی باید با نصب واقعی نود مطابقت داشته باشد. تنها مسیر public certificate خوانده می‌شود؛ private key به پنل منتقل نمی‌شود.

**Renew now** یک job ثبت می‌کند. موفقیت Certbot به‌تنهایی کافی نیست: باید تاریخ انقضا جلو رفته باشد. سپس reload واحدِ تنظیم‌شده اجرا می‌شود. اگر واحدی تنظیم نشده باشد، نتیجه `reload_required` است؛ UI این حالت را نشان می‌دهد و گواهی جدید لزوماً هنوز توسط فرایند پنل سرو نشده است. اگر TLS در CDN یا reverse proxy خارجی terminate می‌شود، آن گواهی توسط عامل محلی مدیریت نمی‌شود.

`Node trust certificate` برای احراز هویت نود است. تعویض یک‌طرفهٔ آن اتصال پنل و نود را خراب می‌کند؛ در این نسخه تاریخ آن نمایش داده می‌شود، ولی تمدید/چرخش هماهنگ هنوز پیاده‌سازی نشده است.

## WARP و Outbounds

Feature **WARP Outbounds** را فعال کنید. پروفایل WireGuard معتبر متعلق به حساب WARP را وارد کنید؛ کلیدها باید ۳۲ بایت Base64 باشند. یک tag با پیشوند `hs-warp-`، Core مقصد و دامنه‌ها یا inboundهای مدنظر را انتخاب کنید. اگر هم دامنه و هم inbound انتخاب شوند، شرط‌ها با هم لازم‌اند.

پیش‌نمایش اطلاعات secret را برنمی‌گرداند. هنگام Apply، revision تنظیمات Core باید با پیش‌نمایش برابر باشد؛ سپس مسیر validation اصلی PasarGuard اجرا می‌شود. نسخهٔ قبلی برای بررسی در `services/core-backups.json` نگه‌داری می‌شود. گزینهٔ restart فقط نودهای Core مربوطه را هدف می‌گیرد. اتصال WARP تا قبل از تست روی نود به‌عنوان سالم گزارش نمی‌شود.

## Telegram MTProxy

روی سرور انتخابی، ابتدا `plugin/install-mtproxy.sh` را اجرا کنید. اسکریپت سورس رسمی Telegram را روی commit ثابت `f36d8af769ffaeac36978d38c2c0f6d1104c2137` می‌سازد و licenseهای upstream را حفظ می‌کند. پیش‌نیازها: `git`، `make`، compiler و development headers مربوط به OpenSSL/zlib.

Feature **Telegram MTProxy** را فعال و از تب Telegram Proxy سرور، دامنه/IP عمومی، پورت client و پورت آمار را وارد کنید. agent تداخل پورت را بررسی، secret تصادفی ایجادشده در پنل را دریافت، و واحد اختصاصی `hs-mtproxy-<id>.service` را راه‌اندازی می‌کند. تنظیمات و secretها فقط روی state محافظت‌شده نگه‌داری می‌شوند. عملیات فقط روی سرویس‌های ساخته‌شده توسط HS انجام می‌شود.

پروتکل استاندارد رسمی با random padding (`dd`) ارائه شده است. تنظیمات upstream تلگرام از endpoint رسمی هنگام ایجاد دریافت می‌شود؛ به‌روزرسانی دوره‌ای آن هنوز خودکار نیست. ترافیک end-to-end و دسترسی کاربران باید روی سرور مقصد آزمایش شود.

## Fair Use — کار باقی‌مانده

آستانه بر اساس `used_traffic` همان کاربر در چرخهٔ جاری سهمیه است؛ حجم بین کاربران جمع نمی‌شود. مثال: baseline برابر 100 Mbps و درصد 20، نرخ هدف را **20 Mbps** می‌کند. نرخ 2 Mbps نیاز به درصد 2 دارد. GB در فرم decimal، برابر یک میلیارد بایت است.

برای کاربر active که به آستانه رسیده، evaluator وضعیت مشتق‌شدهٔ `fair_limited` و رنگ نارنجی `#ea580c` را محاسبه می‌کند. وضعیت‌های `expired`، `disabled`، `limited` و `on_hold` مقدم‌اند. فقط سیاست‌های Hostهای مجاز همان کاربر در محاسبه شرکت می‌کنند. reset مصرف، نتیجه را مجدداً به active برمی‌گرداند. هاست‌های inbound مشترک نمی‌توانند نرخ‌های متفاوت داشته باشند.

**این نتیجه فعلاً پیش‌نمایش است.** تکمیل نیازمند:

- adapter واقعی نود برای محدودیت هر کاربر/مسیر، همراه تست نرخ روی چند اتصال همزمان و TCP/UDP؛
- حفظ مسیر WARP و قواعد outbound هنگام shaping؛
- اعمال محدودیت با شناسهٔ کاربر، بدون محدود کردن همهٔ کاربران نود؛
- هماهنگ‌سازی ACK اجرای نود با نمایش Fair limited و فیلتر سابسکریپشن؛
- ادغام وضعیت مشتق‌شده در لیست/فیلتر کاربران و فرم native Host، بدون خراب کردن وضعیت‌های اصلی یا migration ناسازگار؛
- آزمون بازگشت پس از reset/خاموش کردن feature و عدم دور زدن محدودیت با کانفیگ‌های قبلی.

تا این موارد تست نشوند، فعال کردن Fair Use عمداً رد می‌شود. هیچ ادعای اجرای محدودیت واقعی از UI یا API این نسخه انجام نمی‌شود.

## آزمون‌ها

```bash
python -m pip install -r tests/requirements.txt
python -m pytest -q
npm ci --prefix tests
npm --prefix tests run test:dom
cd tests
npx playwright install chromium
npm run test:browser
```

CI علاوه بر این، قواعد nft را با `nft --check` در network namespace جدا بررسی می‌کند. این تست‌ها تست حملهٔ زنده، ACME واقعی، اتصال Telegram یا throughput Fair Use نیستند.
